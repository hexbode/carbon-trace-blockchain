# 碳链通 · 联盟链使用说明（Ubuntu / WeBASE 3.x）

本文件说明碳链通在 **Ubuntu 演示环境**中联盟链的组成、启停、自检、合约部署与升级、治理与排障。
适用于 `qidonqi/` 一键脚本拉起的 WSL Ubuntu 演示栈，也可作为正式环境的操作蓝本。

> 业务侧的整体说明见仓库根目录 [README.md](../README.md)；本文件只讲链。

---

## 1. 版本与部署形态

| 项 | 实际值 |
| --- | --- |
| 链平台 | FISCO BCOS **3.17.0**（Build 20260824） |
| 管理组件 | WeBASE 3.1.1（Front / Sign / Node-Mgr / Web） |
| 群组 | `group0`（WeBASE 3.x 的群组标识，不是 1.5.x 的 `1`） |
| 节点数 | 2（`node0` / `node1`），单群组 |
| 合约编译 | solc **0.8.30**（`--via-ir --evm-version london`），路径 `/usr/local/bin/solc-0.8.30` |
| 链安装目录 | `/home/user/webase3-src/deploy/` |
| 业务后端 | `/opt/carbon-trace/app/carbon-trace.jar`（JDK 25） |
| 链访问方式 | 后端 → **WeBASE-Front REST**，不引入区块链 SDK |

FISCO BCOS 节点的 JSON-RPC（8545）在本环境**未对外开放**，所有链上读写统一经 WeBASE-Front。

## 4. 服务启停

五个 WeBASE 单元 + 一个业务后端，均托管给 systemd 并已设置开机自启。

```bash
# 按依赖顺序启动
sudo systemctl start webase-node          # 底层链（内部调用 nodes/127.0.0.1/start_all.sh）
sudo systemctl start webase-sign
sudo systemctl start webase-node-mgr
sudo systemctl start webase-front
sudo systemctl start webase-web
sudo systemctl start carbon-trace

# 反序停止
sudo systemctl stop carbon-trace webase-web webase-front webase-node-mgr webase-sign webase-node

# 状态一览
systemctl list-units 'webase*' 'carbon-trace' --no-pager
systemctl status webase-front --no-pager
```

只重启后端（改配置或换 jar 后）：

```bash
sudo systemctl restart carbon-trace
sudo journalctl -u carbon-trace -n 50 --no-pager      # 或 tail /opt/carbon-trace/logs/app.log
```

> 启动顺序不能颠倒：Front 启动时要做群组握手，链节点没起来会直接失败；后端依赖 Front，提前启动会在首个链调用时报连接错误。

Windows 侧一键入口：`qidonqi\启动系统.bat`（拉起 WSL → 按序启服务 → 轮询接口就绪 → 打开浏览器）。

## 5. 连通性自检

由底向上四层，出问题可立刻定位：

```bash
# 1) 链节点存活：区块高度应是递增整数
curl -s http://127.0.0.1:5002/WeBASE-Front/group0/web3/blockNumber

# 2) Front 自身可用（返回 v3.1.1），并确认交易计数可读
curl -s http://127.0.0.1:5002/WeBASE-Front/config/version
curl -s http://127.0.0.1:5002/WeBASE-Front/group0/web3/transaction-total

# 3) 业务接口可服务（免登录）
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/api/public/enterprises

# 4) 后端聚合健康度（需登录；走节点 RPC + 短缓存，冷启动约 0.6s）
TOKEN=$(curl -s -X POST http://127.0.0.1:8080/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"regulator01","password":"123456","role":"regulator"}' | jq -r .token)
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8080/api/blockchain/health
```

预期：① 返回递增整数；② 返回 `v3.1.1` 且交易计数为 JSON；③ 返回 `200`；④ `status` 为正常、`blockNumber` 与 ① 一致。

> Front 没有 `/group/all` 这类接口（那是 Node-Mgr 的门户接口，需登录）；判断「链是否握手成功」以 `group0/web3/blockNumber` 能否返回数字为准。
>
> 第 4 步要求账号已完成首次改密：若仍带强制改密标记，会返回 `{"code":"PASSWORD_CHANGE_REQUIRED"}`，换一个已改密账号即可。正常返回形如
> `{"mode":"webase","available":true,"groupId":"group0","registryAddress":"0x...","latestBlockNumber":410,"chainTxCount":451}`。

## 6. 合约体系

采用**逻辑与数据分离**，共 5 个合约源文件（`houduan/contracts/`）：

| 合约 | 职责 | 是否存状态 |
| --- | --- | --- |
| `CertRegistryData` | 存证状态：防伪码索引、证书状态、写入者集合 | 是（唯一数据源） |
| `CertRegistryLogicV1` | 存证业务规则（认证、撤销、作废、查询） | 否 |
| `CertRegistryLogicV2` | 在 V1 上增加 `highestCertSeq()` 最高序号视图 | 否 |
| `CarbonCompliance` | 五类合规规则判定，保存阈值/配额等治理参数 | 是 |
| `CbamAnchorRegistry` | CBAM 申报快照哈希锚定（P1） | 是 |

关键约束：

- 数据合约的写函数受 `onlyLogic` 限制，只有**当前生效逻辑合约**能写入；
- 切换逻辑只需数据合约的一笔 `updateLogic` 交易，**历史存证不迁移**；
- 旧逻辑立即失权，继续写入会 `revert NOT_LOGIC`；
- 后端只直连逻辑合约；数据合约地址仅用于治理与升级；
- 合规合约**不持有** registry 地址、不回调存证合约，因此升级存证逻辑不影响合规参数。

### 当前生效地址

配置位置：`/opt/carbon-trace/application-ubuntu.yml` → `carbon.chain.contracts`

| 键 | 地址 | 说明 |
| --- | --- | --- |
| `registry` | `0xfae6bb7c90a35e5f56615fa5c048187efb7de850` | 逻辑合约 V2，后端读写全部走这里 |
| `registry-data` | `0x32ca7384ce27324d13177306e949725832a9e968` | 数据合约，仅治理与升级使用 |
| `compliance` | `0xc6d3e4385c5e6bad797295431352da6f94b70ece` | 合规合约，**不要随存证重部署** |
| `cbam-anchor` | 未配置 | 留空则 CBAM 不写链锚点 |

签名账户：

```yaml
carbon.chain.webase.user-address: "0x32730ab8c0575a9e99b5034705f64379dfe03dd2"
```

该地址必须是数据合约的 writer（`addWriter` 加入），否则写链报 `NOT_WRITER`。

> 环境变量 `CARBON_CHAIN_REGISTRY_ADDRESS` / `CARBON_CHAIN_REGISTRY_DATA_ADDRESS` 可覆盖上述地址，但 `registry.name`（ABI 名）只能改 yml。

## 7. 首次部署

```bash
cd houduan/contracts

# 1) 准备签名账户（二选一）
#    a. WeBASE-Sign 托管（推荐生产，私钥不出 Sign）
curl -X POST 'http://127.0.0.1:5002/WeBASE-Front/privateKey?type=2&userName=carbon-backend'
#    b. Front 本地私钥（演示环境最省事）
curl 'http://127.0.0.1:5002/WeBASE-Front/privateKey?groupId=group0&type=0&userName=carbon-backend'

# 2) 部署：数据合约 + 逻辑合约 + 合规合约 + CBAM 锚点合约 → updateLogic 激活 → 注册 ABI
./deploy-contracts.sh --user 0x<address> --solc /usr/local/bin/solc-0.8.30
```

脚本行为：

1. 用 solc 编译 5 个 `.sol`（`--via-ir`，堆栈过深必须 0.8.13+）；
2. 依次部署 `CertRegistryData`、`CertRegistryLogic*`、`CarbonCompliance`、`CbamAnchorRegistry`；
3. 调数据合约 `updateLogic(logic)` 激活；
4. 把 ABI 注册到 Front，并写回 `houduan/src/main/resources/chain/*.abi.json`；
5. 打印四个地址；加 `--out` 可直接生成完整 yml。

**脚本默认部署 V1，生产推荐 V2**：

```bash
./deploy-contracts.sh --user 0x<address> \
  --logic-contract CertRegistryLogicV2 --initial-seq 0 \
  --solc /usr/local/bin/solc-0.8.30
```

全新链没有历史存证，`--initial-seq 0` 就是真实最高序号。

## 8. 逻辑升级（V1 → V2 或 V2 → V3）

只影响存证逻辑；数据、合规、锚点合约都不动。

### 8.1 前置

1. 确认签名账户是**数据合约 owner**（`owner()` 返回该地址），否则 `updateLogic` 报 `NOT_OWNER`；
2. 查真实链上最高认证序号（见 8.2）；
3. 排好维护窗口（见 8.3）。

### 8.2 查真实链上最高序号

```bash
cd houduan/contracts
./query-highest-seq.sh --data 0x32ca7384ce27324d13177306e949725832a9e968 \
                       --logic 0xfae6bb7c90a35e5f56615fa5c048187efb7de850
```

- 提供 `--logic` 时直接读 `highestCertSeq()`，一次调用；
- 逻辑仍是 V1（无该视图）时自动逐块扫描数据合约 `certIdsInBlock(height)` 取最大序号，可用 `--from` / `--jobs` 调优；
- 数据合约 ABI 未注册时先 `--register`。

**不能只看业务库 `MAX(id)`**：链上只追加不删除，删除排放只把存证标记 `INVALID`，撤销只标记 `REVOKED`。业务库删过最高编号后，`MAX(id)` 会偏小。

`--initial-seq` 的方向：

| 取值 | 后果 |
| --- | --- |
| 等于真实最高序号 | 正确 |
| 偏大 | 仅多做逐号检查，**安全** |
| 偏小 | 历史编号被当作空闲，**可能复用旧编号，危险** |

### 8.3 维护窗口与时序

```text
停写 → 记基线 → updateLogic → 更新配置/ABI → 重启所有实例 → 验证 → 恢复写入
```

停写范围（这些操作会写链）：

- 审核通过（生成认证存证）
- 监管撤销
- 删除排放记录（链上标记 INVALID）
- CBAM 申报提交 / 确认（写锚点）
- 链上治理写操作（`addWriter` / `removeWriter` / `transferOwner`）
- 历史数据迁移任务（`carbon.chain.migration.enabled=true` 时）

**新增排放记录不写认证存证**，只异步做合规判定与合规镜像写链，可不停。
公共查询、列表、统计等只读接口可继续服务。

### 8.4 执行升级

```bash
./deploy-contracts.sh --user 0x<ownerAddress> \
  --upgrade-logic 0x32ca7384ce27324d13177306e949725832a9e968 \
  --logic-contract CertRegistryLogicV2 \
  --initial-seq <真实最高序号> \
  --solc /usr/local/bin/solc-0.8.30
```

脚本只做三件事：编译并部署新逻辑合约、调 `updateLogic`、注册新逻辑 ABI。
**不部署、不改写合规合约与锚点合约。**

随后：

1. 改 `application-ubuntu.yml` 的 `carbon.chain.contracts.registry.address` 为新逻辑地址（`registry.name` 不变）；
2. 替换 `houduan/src/main/resources/chain/CertRegistryLogic.abi.json`（脚本已写回）并重新打包 jar；
3. 重启**所有**后端实例。

### 8.5 升级后验证

```bash
# 1) 版本号（V1 返回 1，V2 返回 2）
# 2) highestCertSeq() 应等于基线
# 3) 做一笔真实认证：计数 +1、getByCertId 可查、页面有交易哈希
```

用 Front 直接调视图（无需业务账号）：

```bash
curl -s -X POST 'http://127.0.0.1:5002/WeBASE-Front/trans/handle' \
  -H 'Content-Type: application/json' \
  -d '{
    "groupId":"group0",
    "contractName":"CertRegistryLogicV2",
    "contractAddress":"0x<新逻辑地址>",
    "funcName":"highestCertSeq",
    "funcParam":[],
    "contractAbi":[],
    "user":"0x<ownerAddress>"
  }'
```

排障对照：

| 报错 | 含义 |
| --- | --- |
| `NOT_OWNER` | 签名账户不是数据合约 owner |
| `NOT_LOGIC` | 调的是已失权逻辑，检查 `registry.address` |
| `NOT_WRITER` | 业务账户不在 writer 白名单 |

### 8.6 回滚

两种方式，都只需一笔治理交易：

- **方式 A（推荐）**：对新逻辑再执行一次 `--upgrade-logic`，`--logic-contract` 指定回滚目标版本（需重新部署一份该版本逻辑，用当前真实最高序号作 `--initial-seq`）；签名账户必须是数据合约 owner；
- **方式 B**：直接把 `registry.address` 改回旧逻辑地址并重启（无需发交易）。适用于旧逻辑实例仍在链上、且其 `highestCertSeq` 未过期的情况；若旧 V2 实例的最高序号已落后，编号快路径会退化为逐号检查（安全，但慢）。

回滚同样要走维护窗口：数据与存证不受影响，只有写入权限在新旧逻辑之间切换。

## 9. 数据合约迁移（较少使用）

只有以下情况才需要换数据合约：存储结构变更（例如给 writer 集合加数组索引）、需要真正的编号空间重置、或数据合约本身有缺陷。

关键差异：

| 维度 | 逻辑升级 | 数据合约迁移 |
| --- | --- | --- |
| 链上地址 | 数据地址不变，逻辑地址变 | 数据地址变 |
| 历史存证 | 原样保留 | 需逐条重放 |
| `--initial-seq` | 该数据合约真实最高序号（含已作废/撤销） | 迁移集合的最大序号；不迁移填 0 |
| 编号空间 | 延续 | 新旧两套并存，可能重复分配同一 `CR` 号 |

迁移后注意：

- **旧合约仅作归档**，公众核验只查当前配置的逻辑合约；
- 旧链上的 `REVOKED` 可通过「`certify` 后 `revoke`」保留；`INVALID`（排放记录已删除）不会进入新合约；
- 旧合约读取接口不受 `onlyLogic` 限制，仍可直接查；
- 若要求跨代编号唯一，必须抬高新合约的分配起点，`--initial-seq` 只影响检查快路径、不能阻止复用。

完整迁移步骤（含前置 `migration.enabled=false`、低峰执行、迁移后立即关开关）见 [README.md](../README.md) 第 8.3 节。

## 10. 链上治理

存证 writer 白名单存在**数据合约**；合规与锚点各自独立。

| 操作 | 合约 | 权限 |
| --- | --- | --- |
| 查看 owner / 是否 writer | `CertRegistryData` | 任何人 |
| `addWriter` / `removeWriter` | `CertRegistryData` | 仅 owner |
| `updateLogic` | `CertRegistryData` | 仅 owner |
| 合规阈值 / 配额 | `CarbonCompliance` | 合约 owner |
| CBAM 锚点 writer | `CbamAnchorRegistry` | owner |

平台内入口：监管端「链上治理」页（`/chain-governance`），查询 regulator/admin 可用，变更仅 admin。
也可用 `houduan/contracts/deploy-contracts.sh` 或 WeBASE 控制台直接发交易。

> writer 列表状态存在**数据合约**。若要「列出全部 writer」，现结构没有数组索引，属存储结构变更，**必须新数据合约 + 迁移**，不能靠新逻辑版本解决。

## 11. 浏览器控制台

本环境的登录信息：

| 项 | 值 |
| --- | --- |
| 访问地址 | `http://localhost:5000`（WSL 内为 `http://127.0.0.1:5000`） |
| 账号 | `admin` |
| 密码 | 部署时设定（仓库不记录明文） |
| 账号状态 | `2` = NORMAL（正常） |
| 角色 | `role_id=100000`（管理员） |

> 控制台账号存在 node-mgr 的 MySQL 库 `webasenodemanager.tb_account_info`，**只能重置、无法找回**。
> 状态值含义（取自 `WeBASE-Node-Manager.jar` 的 `AccountStatus` 枚举）：`1=UNMODIFIEDPWD`、`2=NORMAL`、`3=FROZEN`、`4=CANCEL`。
>
> **务必注意：库里存的不是 `BCrypt(明文)`，而是 `BCrypt(sha256(明文))`。** 登录页前端先对密码做 SHA-256，再把十六进制摘要作为 `accountPwd` 发给后端，后端只做一次 BCrypt 比对（`SecurityConfig` 用 `BCryptPasswordEncoder`，登录表单字段为 `account` / `accountPwd`）。若按 `BCrypt(明文)` 写入，哈希本身能校验通过，但登录永远失败。
>
> 若忘记密码，用下面的方式重置（在 WSL 内执行，把 `<新密码>` 换成你要设置的值）：

```bash
# 在 WSL Ubuntu 内以 root 执行
python3 - <<'PY'
import hashlib, subprocess, bcrypt
pwd = b"<新密码>"                                   # 在这里填入要设置的密码
digest = hashlib.sha256(pwd).hexdigest()          # 先 SHA-256，与控制台前端一致
h = bcrypt.hashpw(digest.encode(), bcrypt.gensalt(rounds=10, prefix=b"2a")).decode()
subprocess.run(["mysql", "-e",
  "UPDATE webasenodemanager.tb_account_info SET account_pwd='%s', account_status=2, "
  "login_fail_time=0, modify_time=NOW() WHERE account='admin';" % h], check=True)
print("reset ok:", h)
PY
```

> 该命令等价于直接改库；若 `bcrypt` 模块缺失，先 `apt install python3-bcrypt`。
>
> 验证方式（无需浏览器）：先取验证码 token，再从 node-mgr 日志取该次验证码明文，最后以表单方式调登录接口；返回 `code:0` 即成功。
>
> ```bash
> # 1) 取验证码（同时把 token 记下来）
> curl -s http://127.0.0.1:5001/WeBASE-Node-Manager/account/pictureCheckCode
> # 2) 立刻从日志取这次验证码明文（AccountController 会打印 new checkCode:xxxx）
> grep -o 'new checkCode:[A-Za-z0-9]*' /home/user/webase3-src/deploy/webase-node-mgr/log/WeBASE-Node-Manager.log | tail -n 1
> # 3) 登录；accountPwd 必须是 sha256(明文) 的十六进制
> PWD_SHA=$(printf %s '<新密码>' | sha256sum | cut -d' ' -f1)
> curl -s -X POST "http://127.0.0.1:5001/WeBASE-Node-Manager/account/login?checkCode=<验证码>" \
>   -H 'Content-Type: application/x-www-form-urlencoded' \
>   -H 'token: <第一步返回的 token>' \
>   --data-urlencode "account=admin" \
>   --data-urlencode "accountPwd=$PWD_SHA"
> ```

登录后可做：

- **合约管理** → 按地址添加 `CertRegistryLogicV2` / `CertRegistryData` / `CarbonCompliance`，可直接调用方法与发交易；
- **交易回执** → 粘贴交易哈希查看执行结果与事件；
- **区块** → 按高度看区块内交易。

控制台适合排查与手工治理，业务操作仍走平台页面。

**注意**：控制台监听 `0.0.0.0:5000`，但 Windows 只做了 8088/8443 两条端口映射，因此局域网设备访问 `http://<内网IP>:5000` 会连接失败，只能在 Windows 本机用 `localhost:5000`。需要局域网访问时，用管理员 PowerShell 追加映射：

```powershell
netsh interface portproxy add v4tov4 listenaddress=0.0.0.0 listenport=5000 connectaddress=127.0.0.1 connectport=5000
netsh interface portproxy add v4tov4 listenaddress=0.0.0.0 listenport=5002 connectaddress=127.0.0.1 connectport=5002
New-NetFirewallRule -DisplayName "WeBASE 5000/5002" -Direction Inbound -LocalPort 5000,5002 -Protocol TCP -Action Allow
```

> 这会把链管理入口暴露到局域网，只建议在隔离的演示网络中开启。

## 13. 故障排查

| 现象 | 根因 | 处理 |
| --- | --- | --- |
| Front 启动失败 | 链节点未就绪 | 先 `systemctl start webase-node`，等 20200/20201 监听 |
| 写链 `NOT_WRITER` | `user-address` 不在数据合约白名单 | 数据合约 `addWriter`，或换签名账户 |
| 写链 `NOT_LOGIC` | 调用了已失权逻辑 | 核对 `registry.address` 是否为当前逻辑 |
| 写链 `NOT_OWNER` | 治理交易签名账户不是 owner | 换 owner 账户签名 |
| 核验返回 422 / `201510` | Front 对「不存在的交易哈希」返回 422 | 已完成修复：按「未找到」处理，不再当链故障 |
| 列表里交易哈希为空 | 存证写在旧逻辑合约，网关按当前地址过滤 | 属正常；详情与核验仍按区块回查 |
| 合约调用普遍 ~2.16 s | Front 每次调用新建 SDK 客户端 | 已知下限，已用缓存/并行规避；进一步需改 Front |
| 后端启动后首个请求超时 | Front 尚未就绪 | 轮询 `/api/public/enterprises` 返回 200 再访问 |
| 区块高度长时间不变 | 节点掉线或磁盘满 | `df -h`、`tail nodes/127.0.0.1/node0/log/*.log` |

## 14. 安全与运维注意

- **私钥**：生产用 WeBASE-Sign 托管（`--sign-user-id`），不要使用 Front 本地私钥；`--user` 只传地址；
- **owner 账户**：`updateLogic` 与 writer 变更都由数据合约 owner 控制，建议离线或多签保管；
- **合规合约不要重部署**：阈值/配额只存在当前实例，换新实例会以代码默认值运行、历史参数丢失；
- **不要直接改链上数据**：链上只追加不删除，删除业务数据只能标记 `INVALID`，撤销为终局状态；
- **备份**：每次升级/迁移前备份 `application-ubuntu.yml` 与数据库到 `/opt/carbon-trace/backups/`；
- **单写实例**：`highestCertSeq` 缓存是进程内的，多实例部署时缓存滞后会退化为逐号检查（安全但慢），建议保持单写实例或使用共享缓存。
